# Cartouche local-game and Wine research

## 1. Steam library while client is closed

**Recommendation:** Treat `localconfig.vdf` as UI/activity metadata, not ownership. Expose a distinct “installed locally” list from `steamapps/appmanifest_<appid>.acf`; for full purchased library while Steam is closed, use the Steam client’s own exported library (`steam-library.json`, account-scoped and refreshed while logged in), clearly label it cached/stale. There is no dependable, complete plaintext local ownership database guaranteed by Valve.

`userdata/<accountid>/config/localconfig.vdf` (UserLocalConfigStore/Software/Valve/Steam/apps) records per-user client state for apps Steam has encountered/configured on this machine; it is not a canonical entitlement ledger and omits uninstalled/never-touched owned titles. `appcache/appinfo.vdf` is app metadata (name/type etc.), not licenses; `packageinfo.vdf` describes packages/subscriptions but does not by itself prove present account entitlement. `config/loginusers.vdf` identifies cached accounts, not their licenses. `sharedconfig.vdf` holds user preferences/collections, not complete ownership. `libraryfolders.vdf` plus each `steamapps/appmanifest_<appid>.acf` is reliable for installed titles only. `userdata/<id>/7/remote/sharedconfig.vdf` / remotecache and cloud saves describe user configuration/saves, not ownership. `config/licensecache` may contain cached licensing data in Steam-specific binary/encrypted format and is undocumented/unstable; do not parse as supported ownership source. SteamDB’s parser docs describe appinfo/packageinfo as app/package metadata: https://github.com/SteamDatabase/SteamAppInfo

Without API key or login: locally cached data can be read without contacting Steam, but only installed titles or cached client-export data can be reliably surfaced. A complete current owned list requires Steam-authenticated account access (Steam client or Web API with user authentication); Steam’s public API has no arbitrary-user owned-games endpoint without a key and user authorization. Valve API docs: https://partner.steamgames.com/doc/webapi/IPlayerService#GetOwnedGames

For `appinfo.vdf` (often 100+ MB), avoid reading/decoding whole file on UI/polling paths. Its binary format is a header and length-delimited app records; build a streaming/indexed reader, skip payloads for IDs you do not need, and cache offsets/results keyed by file size + modification time (and format version). Re-read only when metadata changes; do not repeatedly parse it to infer ownership.

Local implementation context: `app/Sources/NotProtonApp/Library/Steam/SteamLocalFiles.swift` reads `libraryfolders.vdf`, `loginusers.vdf`, and caches app manifests by mtime; `SteamLibraryImport.swift` already consumes `steam-library.json` for broader owned list and merges installed manifests.

## 2. Finding a real game executable

**Recommendation:** Use an explicit, confidence-ranked resolver: parse Unreal `.uproject`/layout first and choose `Binaries/Win64/<Project>-Win64-Shipping.exe`; otherwise inspect PE metadata/imports and launcher configuration, then allow user override. Do not rely on the top-level executable name or file size alone.

For Unreal, enumerate `*.uproject` (JSON) under game root; project basename is the target stem. Candidate `Game/Binaries/Win64/Game-Win64-Shipping.exe` and `Game/Binaries/Win64/Game.exe`; select Shipping when present. Also support `Engine/Binaries/Win64` only for engine tools, not game. Validate candidate is PE and architecture matches. Epic’s documentation describes packaged Windows output and project binaries: https://dev.epicgames.com/documentation/en-us/unreal-engine/packaging-your-project

Other patterns are not universal. Unity `UnityCrashHandler64.exe` is a crash reporter, not the game; executable is usually `<Game>.exe` beside `<Game>_Data/` (Unity docs: https://docs.unity3d.com/Manual/WindowsStandaloneBinaries.html). Paradox Launcher is a separate launcher; locate game-specific exe in install directory/config/manifest, not launcher install. Bethesda launchers (`*_Launcher.exe`) commonly front `*_x64.exe`/game executable; prefer game binary corroborated by companion `Data` directory and PE imports. RE Engine often has `<Game>.exe` plus `re_chunk_000.pak`; no stable cross-title naming rule—inspect package/config and allow override. Treat these as heuristics and retain launcher fallback; launching the wrong binary can bypass required arguments/anti-cheat.

## 3. Fresh Wine prefix initialization

**Recommendation:** Make prefix creation a serialized, explicit setup phase before enabling Play. Run CrossOver’s supplied `wineboot`/prefix update to completion, show progress/log and cancellation, then verify `wineserver -w` and a successful boot before launching any game. Never share a concurrently initializing prefix. Do not assume 11 minutes is expected or attribute it solely to Rosetta: measure logs/stages and retain the error output.

Fresh Wine prefixes create registry/configuration, user directories, font caches and system links; optional Mono/Gecko downloads/install can add substantial time. On Apple Silicon, x86_64 Wine/game components may also incur Rosetta translation/cache warm-up, but no evidence establishes it as the sole cause. Local CrossOver 26.3 experiment at `/tmp/cx-lab/REPORT.md`: interrupted or still-initializing prefix caused `explorer failed to start` and generic `nodrv_CreateWindow`; uninterrupted repair took 670.94 seconds, while a repaired cold `wine winecfg` window took 37.5 seconds. Wine timed out at five minutes but continued prefix installation: `.update-timestamp` is not completion proof. Repair command used `wineboot.exe -u`, `WINEBOOTSTRAPMODE=1`, and `WINEDLLOVERRIDES='mscoree,mshtml='`; overrides were repair-specific and not needed after completion. See Wine boot code/docs: https://gitlab.winehq.org/wine/wine/-/blob/master/programs/wineboot/wineboot.c and https://wiki.winehq.org/FAQ#How_do_I_install_Wine_Mono.3F

Launcher patterns differ by product/version; avoid assuming a universal copied template. CrossOver manages bottles and installs into them; Whisky creates per-game bottles/prefixes; Heroic/Lutris/Bottles generally create/configure prefixes on demand and may use templates/runners, but those are mutable implementation details, not a robust compatibility contract. A preinitialized template can reduce user wait, but copying a prefix across machine/user paths risks stale absolute paths, runner version mismatch and shared identity/config; if used, generate per runner version and run prefix update after copy. Cartouche should default to CrossOver runner while doing first-time setup on a background task, report “Preparing Windows environment” with meaningful indeterminate/phase progress, use isolated prefix per game (or deliberate shared bottle), prevent starts until complete, and provide retry/recreate. Use `wineserver -w` only after the boot command exits to drain processes, then verify expected registry/system files and launch a known small probe; preserve logs. Keep optional Mono/Gecko policy explicit—disabling via `mscoree,mshtml=` avoids those downloads but can break .NET/HTML apps, so do not silently apply globally.
